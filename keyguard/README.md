# keyguard

Единственный сервис, который видит ключи API пользователей (`docs/ARCHITECTURE-v2.md`, раздел 5). Пространства к
моделям и Git ходят только через него: предъявляют свой токен, keyguard подставляет ключ владельца или спонсора и
считает расходы. Go 1.26, стандартная библиотека и одна внешняя зависимость — драйвер Postgres `lib/pq`.

История решений — `fugu-deck-infra/docs/decisions.md` (D20, D22–D25, D28–D30); найденные и исправленные ошибки —
`fugu-deck-infra/docs/security-review.md`.

## Что делает

| Путь | Кто вызывает | Что |
|---|---|---|
| `POST /v1/keys` | control-plane | ввод ключа: `{jws, enc, ct}` — подписанное действие `key_put` + HPKE-шифротекст → проверка → пробный запрос к провайдеру → OpenBao, в ответ маска |
| `POST /v1/grants` | control-plane | разрешение спонсора (подписанное действие `grant`) |
| `POST /v1/grants/activate` | общее пространство | модель утверждена — разрешение своего пространства становится активным |
| `POST /v1/grants/revoke` | control-plane | отзыв (подписанное действие `grant_revoke` — по чату и предложению, только спонсор) |
| `POST /v1/grants/member-left` | control-plane | участника исключили: его разрешения отозваны, из чужих в этом пространстве он убран (только сужение прав, D68) |
| `POST /v1/account/purge` | space-operator | удаление аккаунта: ключи, устройства, разрешения спонсора — не раньше 23 ч после проверки подписи `account_delete` (D52) |
| `POST /v1/account/cancel` | control-plane | удаление аккаунта отменено — проверенная подпись больше ничего не сотрёт |
| `POST /v1/actions/verify` | space-operator, ssh-gateway | проверка подписи действия, которое исполнитель собирается выполнить (`space_delete`, `account_delete` / `ssh_write`, `ssh_danger`, `server_add`, `agent_rights`); в ответ действие и подписавший |
| `POST /llm/anthropic/v1/messages`, `POST /llm/sakana/v1/chat/completions` | пространства | прокси моделей: подстановка ключа, учёт расходов, лимиты |
| `/git/github/…`, `/git/gitlab/api/v4/…` | пространства | прокси Git: белый список ровно тех вызовов, что делает агент (`git.go`); без удаления репозиториев, deploy-ключей, webhook, секретов CI, force-push |
| `POST /v1/devices/challenge` | control-plane (`join/v1/enroll/challenge`) | одноразовый вызов для аттестации (15 минут); приложение берёт его до создания ключей |
| `POST /v1/devices` | control-plane (`join/v1/enroll`) | регистрация устройства: токен Keycloak с `cnf.jkt` + DPoP + действие `device_enroll` + CSR + аттестация; устройство ждёт подтверждения |
| `POST /v1/devices/confirm`, `/v1/devices/revoke` | control-plane | подписанное действие устройства того же пользователя или администратора; при подтверждении — сертификат из OpenBao `pki-device` |
| `POST /v1/devices/revoked` | control-plane | ID отозванных устройств: control-plane не пускает их на api сразу (D63) |
| `POST /v1/egress`, `/v1/egress/list` | control-plane | домены для агента: подписанное действие `egress_set` (список целиком), список (D65) |
| `GET /v1/egress/mine`, `GET /egress/fetch?url=…` | личные пространства | свои домены; страница с домена из списка — только GET, https:443, внутренние адреса запрещены, перенаправления — только внутри списка |
| `POST /v1/devices/status` | control-plane (`join/v1/enroll/status`) | статус, отметка аттестации и сертификат mTLS; доказательство ключом сессии этого устройства |
| `/healthz`, `/readyz` | kubelet | жив / подключён к базе, вошёл в OpenBao и загрузил ключ HPKE |

Пространство предъявляет проецируемый токен ServiceAccount (audience `keyguard`) **в поле ключа API** своего SDK
(`x-api-key` или `Authorization: Bearer`). keyguard проверяет его через TokenReview, вырезает и подставляет настоящий ключ.

## Подписанные действия

Всё, что меняет ключи, разрешения и устройства, приходит как действие, подписанное на телефоне ключом подтверждения
(биометрия). control-plane передаёт его как есть и изменить не может.

- **Формат** — компактный JWS (`{"jws": "…"}`): заголовок `{"alg":"ES256","typ":"deck-action+jws","kid":<device_id>}`,
  payload — канонический JSON конверта (поля типа + `device_id`, `nonce`, `ts` в секундах, у действий в пространстве —
  `space`), подпись — сырое `r‖s`. Кто подписал, определяет устройство, а не поле в действии.
- **Схема** (`schema.go`) — зеркало `fugu-deck-app/mobile/src/core/actions.ts`. До проверки подписи keyguard отклоняет
  неизвестный тип, лишнее или недостающее поле, невидимые и bidi-символы, `space` у действия вне пространства и значения
  не по формату: подписано может быть только то, что приложение показало человеку.
- **Строгий разбор:** дубликаты ключей и не-каноничная форма JSON — отказ; nonce одноразовый; окно времени — 5 минут.
- **Ввод ключа** (`key_put`): ключ API зашифрован на телефоне HPKE (RFC 9180, P-256 / HKDF-SHA256 / AES-128-GCM) с AAD
  `key_put|<device_id>|<provider>|<nonce>`; подпись покрывает хеш шифротекста и `key_hint` — последние 4 символа ключа,
  которые человек видел на экране.
- **Регистрация** (`device_enroll`) — тот же JWS, но подпись проверяется ключом подтверждения из запроса, а `kid` и
  `device_id` обязаны совпасть с ID, который keyguard выводит из этого ключа.
- **Подтверждение и отзыв устройства** (`device_approve`, `device_revoke`): цель — в поле `target`; `user` (и `name` при
  подтверждении) keyguard сверяет со своим реестром — человек подтверждал, глядя именно на них.
- **Общие векторы** — `testdata/action-vectors.json`, их создаёт код приложения (`mobile/tests/vectors.ts`):
  `vectors_test.go` обязан принять каждый из `vectors`, отклонить каждый из `invalid` и иметь вектор на каждый тип схемы.
  Перекрёстная проверка с кодом приложения — `cmd/kgcheck` и `mobile/tests/*.test.ts`.

## Учёт расходов

Перед запросом к провайдеру резервируется максимально возможная стоимость (вход — по размеру тела, выход —
`max_tokens`), после ответа записывается факт провайдера. Под одной блокировкой проверяются все бюджеты запроса:
личный, разрешение спонсора, дневной лимит участника.

- Запрос без `max_tokens` и модель без цены не пропускаются — расход нельзя ограничить.
- Оборванный поток списывает не меньше резерва; успешный ответ без usage — весь резерв; ошибка провайдера — ноль.
- Кэш промптов Anthropic: запись ×2 входной цены (верхняя ставка), чтение ×0,1.
- Тело запроса — белый список полей верхнего уровня и только клиентские инструменты: серверные (web_search,
  code_execution…) тарифицируются мимо токенов. Нужна бета или новое поле — добавляйте в `allowedFields` /
  `forwardHeaders` вместе с ценой.
- Цены Anthropic — `DECK_PRICES_ANTHROPIC="модель=вход:выход,…"` (USD за 1M токенов); цены Sakana зашиты в код.
- В журнале вместо id пользователей — хеши: журнал аудита в prod не удаляется 90 дней.

## Хранение состояния

Устройства, одноразовые номера, разрешения спонсоров, лимиты и расходы лежат в Postgres (база `keyguard`, таблицы
`kg_*` создаются при старте). Память — рабочая копия: чтения в базу не ходят, но каждое изменение сначала
записывается и только потом применяется (`persist.go`, `pg.go`). Ключи API — только в OpenBao.

- **После перезапуска** подпись не повторить (nonce в базе), лимиты не обнуляются, отозванное устройство остаётся
  отозванным, неподтверждённое — неподтверждённым.
- **Расход записывается до запроса к провайдеру** (весь резерв) и уточняется после ответа: падение посреди запроса
  оставляет в учёте резерв — учёт завышается, а не теряется.
- **База недоступна — ничего не принимается «в долг»:** подписанные действия отклоняются, запросы к моделям получают
  503 и к провайдеру не уходят, `/readyz` — 503. Отзыв устройства и разрешения действует сразу, даже если записать
  его не удалось (клиент получает 503 и повторяет).
- **Экземпляр один** — рабочие копии двух процессов разошлись бы. Это держит блокировка в базе
  (`pg_advisory_lock` на отдельном соединении): второй keyguard ждёт и запросов не принимает; потеряв соединение с
  блокировкой, процесс завершается. В манифесте — `replicas: 1`, `strategy: Recreate` (при обновлении — короткий простой).
- **Без базы keyguard не стартует.** `DECK_STATE=memory` — только для стендов.

## Аттестация устройств

При регистрации keyguard проверяет, что ключи созданы в чипе настоящего телефона настоящим приложением (`attest.go`).

- **Android — Key Attestation.** У каждого из двух ключей своя цепочка до корня Google (`roots/android.certs`). Из
  описания ключа проверяются: вызов сервера, уровень (TEE или StrongBox, программный — отказ), ключ создан в чипе и годен
  только для подписи, P-256, загрузчик закрыт и система не изменена, пакет и подпись приложения, у ключа подтверждения —
  требование биометрии. Место хранения в реестре берётся из аттестации, а не со слов приложения.
- **iOS — App Attest.** Цепочка до корня Apple (`roots/apple.certs`), приложение (`<TeamID>.<bundle id>`), боевая
  среда, счётчик 0, привязка к вызову и к обоим ключам устройства. App Attest подтверждает приложение и телефон; на сами
  ключи Secure Enclave Apple цепочку не выдаёт.
- **Вызов** выдаёт keyguard, он одноразовый и живёт 15 минут; перезапуск keyguard гасит выданные вызовы.
- **Режимы** (`DECK_ATTESTATION`): `optional` (по умолчанию) — проверять, если прислана, и отмечать в реестре;
  `required` — без неё не регистрировать; `vouched` — проверять, если прислана, а устройство без неё ждёт подтверждения
  и активируется только подписью устройства, которое само прошло аттестацию (D62); `off`. Присланная, но неверная
  аттестация — отказ в любом режиме, кроме `off`.
- **Восстановление администратора** (`DECK_BOOTSTRAP_RECOVER=1`, включать на время через git): устройство
  `DECK_BOOTSTRAP_ADMIN` подтверждается само, если у него нет действующих устройств (в `vouched`/`required` — только
  аттестованное). Без флага первое устройство администратора активируется само, лишь пока в кластере нет ни одного.
- Платформа без настроек (пакет и подпись приложения, AppID) не принимается вовсе. Корни вшиты в бинарник; источник и
  отпечатки записаны в самих файлах.

## НЕ готово для боя

1. **Аттестация испытана только на Android** (телефоны с TEE и StrongBox в test). iPhone не проверялся. Список
   отозванных ключей аттестации Google не проверяется.
2. **Настоящие API Anthropic и Sakana не вызывались** — только моки; формат usage взят из документации.
3. **Кэш ключей на время, пока OpenBao запечатан** (`ARCHITECTURE-v2.md`, 5.4), не реализован — keyguard перестаёт
   выдавать ключи (`DECK_KEY_CACHE_TTL` в манифесте пока не читается).
4. **Кэш TokenReview 30 с:** токен удалённого ServiceAccount, уже бывший в кэше, принимается до 30 с.
5. **Лимит может быть превышен одним запросом** (провайдер считает токены после ответа). Вторая линия — лимиты расходов
   в консолях провайдеров.
6. **Личный лимит — помесячный** (`spend_limit`, D48): лимит на всё время (`user:<id>`) по-прежнему не задаётся.
7. **Удаление ключа** (`key_delete`) удаляет все версии в OpenBao; кэша ключей нет, так что следующий запрос уже без ключа.
8. **Цены:** тариф длинного контекста есть (`Price.LongAbove`, у Ultra — больше 272K); приоритетные уровни не учитываются.
9. **TLS к базе — `require`:** шифрование без проверки сертификата сервера (как у Keycloak).
10. **Подтверждает устройство** любое устройство того же пользователя или администратор (устройство без аттестации — в
    режиме `vouched` только аттестованное); «подтверждает именно пригласивший» — не сделано.
11. **Переключение primary CNPG** не проверено; сам keyguard работает в кластере test с 09.10.
