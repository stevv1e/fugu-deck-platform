# space-operator

По объекту `Space` (CRD `spaces.deck.fugu` в `deck-system`) создаёт пространство пользователя: namespace `deck-u-<ник>`
с квотами и сетевыми политиками, том и под с агентом (образ `deck-space` — `fugu-deck-app/backend` в режиме `space`)
под gVisor. Входа из интернета у оператора нет; control-plane умеет только создать `Space`. Архитектура — раздел 6.2.

**Готово (в test, 0.6.22):** личные (`deck-u-<ник>`) и общие (`deck-t-<id>`) пространства; остановка и пробуждение
через `spec.suspended` (решает control-plane по неактивности); удаление пространства и аккаунта по подписи владельца
(подпись проверяет сам оператор через keyguard, удаление — после срока на отмену); резервные копии базы и файлов в бакет (ниже) и
восстановление. Litestream не нужен: оператор сам забирает снимки.

Правила, которые оператор соблюдает сам, не полагаясь на control-plane:

- имя личного пространства обязано совпадать с ником владельца — keyguard по namespace `deck-u-<ник>` решает, чьим
  ключом API платить, и пространство с чужим ником в имени не обслуживается;
- без публичного ключа control-plane (аннотация `deck.fugu/token-key`) пространство не запускается: агент не смог бы
  проверить токены входа.

Зависимостей нет: API Kubernetes вызывается напрямую (server-side apply).

```bash
go test -race ./...      # тесты
scripts/kube_test.sh     # настоящий kube-apiserver с правилами допуска платформы: под пространства принимается,
                         # писать вне пространств оператор не может
```

## Резервные копии пространств

Данные пространства — одна база SQLite на томе ноды. Ключа хранилища копий в пространстве нет: оператор сам раз в
`DECK_BACKUP_EVERY` (15 мин) забирает у агента согласованный снимок (`GET /internal/backup`, вход по токену из
Secret `space-backup`) и кладёт его в бакет под ключом `spaces/<имя>/fugu-deck.sqlite3`. Неизменившаяся база повторно
не загружается; перед остановкой агента (сон, ожидание удаления) берётся последний снимок.

- **Восстановление** — только в пустое пространство с новым томом: том создаётся заново, а копия есть → после запуска
  агента оператор передаёт ему копию (`POST /internal/restore`), агент перезапускается с восстановленной базой.
- **Удаление пространства** убирает и копию (в бакете с версиями — метка удаления; прежние версии исчезают по правилу
  жизненного цикла).
- Настройки: `DECK_BACKUP_S3_ENDPOINT`, `_REGION`, `_BUCKET`, `_ACCESS_KEY`, `_SECRET_KEY`. Без бакета копии выключены.
- Проверка клиента S3 на настоящем хранилище: `S3_TEST_ENDPOINT=… S3_TEST_REGION=… S3_TEST_BUCKET=…
  S3_TEST_ACCESS_KEY=… S3_TEST_SECRET_KEY=… go test -run TestS3OnRealStorage .`
